一、当前系统分析

现有架构

流萤当前的记忆系统基于 core/memory.py，核心能力：

能力实现方式状态
持久化存储SQLite（messages 表）✅ 已实现
全文检索FTS5 trigram 分词✅ 已实现（降级为 LIKE）
记忆分类对话/笔记/待办/备忘✅ 已实现
重要度评分0-10 整数✅ 已实现
记忆关联related_ids JSON 数组✅ 已实现
语义检索向量嵌入 + 相似度搜索❌ 未实现
记忆摘要/压缩自动总结长对话❌ 未实现
实体/关系抽取知识图谱❌ 未实现
自适应记忆管理自动遗忘/巩固❌ 未实现

当前记忆召回流程

用户输入 → memory.build_recall_block(query, top_k=5) ↓ FTS5 / LIKE 关键词匹配 ↓ 返回最近 5 条匹配记录（时间倒序） ↓ 拼入 System Prompt: "【你记得的与当前话题相关的往事】" ↓ LLM 生成回复

核心瓶颈：当前依赖纯关键词匹配，无法处理语义相关但关键词不同的查询。例如用户说"上次讨论的那个方案"，系统无法找到相关记忆。

二、记忆架构全景（业界 2026 最佳实践）

2026 年生产级 AI 记忆系统通常采用五层记忆架构：

层级名称存储生命周期延迟要求
1工作记忆进程内状态当前轮次<1ms
2短期记忆最近 N 轮对话当前会话<10ms
3长期记忆结构化数据库跨会话永久<50ms
4语义记忆向量数据库 + BM25跨会话永久<200ms
5情景记忆会话日志 + 向量索引跨会话永久<500ms

流萤当前覆盖了第 1-3 层（部分），缺失第 4-5 层。以下方案聚焦于补齐语义记忆和情景记忆能力。

三、方案 A：增强型关键词检索（渐进改良）

难度：低 周期：1-2 天

核心思路

不引入新依赖，在现有 SQLite + FTS5 基础上增强检索质量。

技术架构

用户输入 ↓ ┌─────────────────────────────┐ │ 查询预处理（Query Rewrite） │ │ · 去除停用词 │ │ · 同义词扩展 │ │ · 提取关键实体 │ └─────────┬───────────────────┘ ↓ ┌─────────────────────────────┐ │ 多路召回（Hybrid Recall） │ │ ① FTS5 trigram 全文匹配 │ │ ② LIKE 模糊匹配 │ │ ③ 按分类/标签过滤 │ │ ④ 按重要度排序 │ └─────────┬───────────────────┘ ↓ ┌─────────────────────────────┐ │ 结果融合 + 去重 + 重排序 │ │ · BM25 得分加权 │ │ · 时间衰减因子 │ │ · 重要度加权 │ └─────────┬───────────────────┘ ↓ 注入 System Prompt

实现步骤

  1. 查询改写模块：用 LLM 或规则将口语化查询转为检索友好格式 
    def rewrite_query(raw: str) -> str:
    """规则 + 简单 NLP 改写查询"""
    # 去除口语填充词
    # 提取核心关键词
    # 同义词扩展（本地词典）
  2. 多路召回融合：同时执行 FTS + LIKE + 分类过滤，按分数融合
  3. 时间衰减：近期记忆权重更高，但重要记忆不受影响 
    def recency_boost(ts: int, half_life_days=30) -> float:
    age_days = (time.time() - ts) / 86400
    return 2 ** (-age_days / half_life_days)
  4. 自动摘要：长对话自动压缩，保留关键信息
  • 零新依赖，纯 Python + SQLite
  • 打包体积不变，无额外运行时开销
  • 实现简单，1-2 天可完成
  • 与现有架构完全兼容
  • 无法处理真正的语义搜索（同义词/近义词）
  • 中文分词质量受限于 FTS5 trigram
  • 记忆量大时召回精度下降
  • 无法发现隐含的关联记忆
适用场景

记忆量 < 5000 条、用户不追求"语义理解"、优先稳定性和打包体积的场景。

四、方案 B：本地向量检索（RAG）

难度：中 周期：3-5 天

核心思路

引入 Embedding 模型 + 向量存储，实现语义级别记忆检索。核心参考：OpenClaw 的本地 SQLite + sqlite-vec 架构。

技术架构

对话存储 ↓ ┌─────────────────────────────┐ │ 消息写入 messages 表 │ │ 同时调用 Embedding 模型 │ │ 生成向量 → chunks_vec 表 │ └─────────────────────────────┘ 用户查询 ↓ ┌─────────────────────────────┐ │ 查询向量化 │ │ 调用同一 Embedding 模型 │ └─────────┬───────────────────┘ ↓ ┌─────────────────────────────┐ │ 向量相似度搜索 │ │ SQLite + sqlite-vec 扩展 │ │ 或纯 Python 余弦相似度兜底 │ └─────────┬───────────────────┘ ↓ Top-K 相关记忆 → 注入 Prompt

Embedding 模型选型

模型维度中文部署方式打包体积增加
m3e-base（推荐）768✅ 专项优化ONNX 本地推理~400MB
BGE-small-zh512✅ONNX 本地推理~200MB
nomic-embed-text768⚠️ 一般ONNX 本地推理~300MB
text-embedding-3-small1536✅OpenAI API~0MB（需联网）

实现步骤

  1. 安装依赖： 
    pip install sentence-transformers onnxruntime  # 本地推理
# 或
pip install openai  # API 方式
  2. 扩展 SQLite Schema： 
    -- 新增向量存储表
CREATE TABLE IF NOT EXISTS chunks_vec (
    id INTEGER PRIMARY KEY,
    embedding BLOB NOT NULL,  -- float32 二进制向量
    model TEXT NOT NULL
);

-- 或使用 sqlite-vec 扩展（更高效）
-- CREATE VIRTUAL TABLE chunks_vec USING vec0(embedding float[768]);
  3. 向量化写入：每次 add() 消息时，同时生成 embedding 存入 chunks_vec
  4. 向量搜索： 
    def vector_search(query: str, top_k: int = 5) -> list[dict]:
    # 1. 查询向量化
    q_vec = embed(query)
    # 2. 加载所有向量（小规模）或用 sqlite-vec 加速
    # 3. 计算余弦相似度
    # 4. 返回 Top-K
    results = []
    for row in db.execute("SELECT id, embedding FROM chunks_vec"):
        sim = cosine_similarity(q_vec, deserialize(row['embedding']))
        results.append((row['id'], sim))
    results.sort(key=lambda x: -x[1])
    return results[:top_k]
  5. 混合检索：向量搜索 + FTS5 关键词搜索结果融合
  6. 优雅降级：sqlite-vec 不可用时回退到纯 Python 余弦计算
  • 真正的语义搜索，"同义词/近义词"也能命中
  • 本地运行，数据完全隐私
  • 与现有 SQLite 架构天然兼容
  • OpenClaw 已验证此架构在桌面端可行
  • 打包体积增加 200-400MB（Embedding 模型）
  • 首次推理较慢（模型加载 ~2-5 秒）
  • 查询延迟增加 50-200ms
  • 需要处理 sqlite-vec 跨平台兼容性
适用场景

追求语义理解能力、用户记忆量较大（5000+）、可接受打包体积增加的场景。这是性价比最高的方案。

五、方案 C：知识图谱 + 向量混合

难度：高 周期：7-10 天

核心思路

在向量检索基础上，增加实体-关系图谱，支持关系推理。参考"Building a Local-First Memory Layer for AI Agents"的 SQLite + 内存图架构。

技术架构

对话存储 ↓ ┌─────────────────────────────┐ │ 消息写入 messages 表 │ │ ↓ │ │ LLM 实体/关系抽取 │ │ · entities 表 │ │ · relations 表（S-P-O 三元组）│ │ ↓ │ │ 向量嵌入 → chunks_vec 表 │ └─────────────────────────────┘ 用户查询 ↓ ┌─────────────────────────────┐ │ 双路召回 │ │ ① 向量语义搜索 → 候选记忆 │ │ ② 提取查询中的实体 │ │ → 图谱 BFS/DFS 遍历 │ │ → 获取关联实体和关系 │ └─────────┬───────────────────┘ ↓ ┌─────────────────────────────┐ │ 结果融合 │ │ · 向量得分 + 图谱关联度 │ │ · 结构化上下文组装 │ └─────────┬───────────────────┘ ↓ 注入 System Prompt

数据模型

-- 实体表
CREATE TABLE entities (

实现步骤

  1. 在方案 B 基础上，增加实体/关系抽取（用 LLM 后处理每轮对话）
  2. 构建内存图（启动时从 SQLite 加载，增量更新）
  3. 查询时双路召回：向量搜索 + 图谱遍历
  4. 结果融合排序
  • 支持关系推理（"谁负责的项目"）
  • 结构化知识，可解释性强
  • 本地 SQLite 存储，零运维
  • 实现复杂度高，需要 LLM 抽取实体/关系
  • 每轮对话额外消耗 LLM token（抽取用）
  • 实体对齐和冲突处理较难
  • 打包体积增加最多
适用场景

需要复杂关系推理（如项目管理、团队协作）、有明确实体-关系需求的场景。对个人助手来说可能过度设计。

六、方案 D：三层混合记忆架构（⭐ 推荐）

推荐方案 难度：中 周期：5-7 天

核心思路

结合方案 A 和方案 B 的优点，采用三层混合架构：缓冲层（最近对话原文）+ 摘要层（会话压缩）+ 向量层（长期语义检索）。这是 2026 年生产级 AI 助手的最佳实践。

技术架构

┌─────────────────────────────────────────────────────┐ │ 三层记忆架构 │ │ │ │ ┌─────────────────────────────────────────────┐ │ │ │ Layer 1: 缓冲层（Buffer） │ │ │ │ · 最近 8-10 轮对话原文 │ │ │ │ · 始终注入 System Prompt │ │ │ │ · 无延迟，保证对话连贯性 │ │ │ └─────────────────────────────────────────────┘ │ │ ↓ │ │ ┌─────────────────────────────────────────────┐ │ │ │ Layer 2: 摘要层（Summary） │ │ │ │ · 当前会话的压缩摘要 │ │ │ │ · 每 10 轮自动触发 LLM 摘要 │ │ │ │ · 保留关键决策/偏好/上下文 │ │ │ └─────────────────────────────────────────────┘ │ │ ↓ │ │ ┌─────────────────────────────────────────────┐ │ │ │ Layer 3: 语义层（Semantic） │ │ │ │ · 全量历史对话的向量索引 │ │ │ │ · 用户最新输入触发语义检索 │ │ │ │ · 返回 Top-5 相关历史片段 │ │ │ │ · 混合检索：向量 + FTS5 + 重要度 │ │ │ └─────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────┘ 用户新输入 ↓ ┌─────────────────────────────────────────────────┐ │ 上下文组装（Context Assembly） │ │ │ │ System Prompt = │ │ [人设] │ │ + [Layer 1: 最近 8 轮原文] │ │ + [Layer 2: 会话摘要] │ │ + [Layer 3: 语义检索结果 Top-5] │ │ + [用户输入] │ │ │ │ → 发送给 LLM 生成回复 │ └─────────────────────────────────────────────────┘

实现步骤

Step 1：扩展 memory.py — 增加向量存储

class Memory:
    def __init__(self, db_path: str):
        # ... 现有代码 ...
        self._init_vec_tables()  # 新增

    def _init_vec_tables(self):
        """初始化向量存储表"""
        cur = self.conn.cursor()
        # 向量索引表（sqlite-vec 或兜底方案）
        cur.execute("""
            CREATE TABLE IF NOT EXISTS vec_memories (
                id INTEGER PRIMARY KEY,
                embedding BLOB,
                model TEXT DEFAULT 'm3e-base'
            )
        """)
        self.conn.commit()

    def add_with_embedding(self, session_id, role, content, **kwargs):
        """写入消息 + 同时生成向量"""
        msg_id = self.add(session_id, role, content, **kwargs)
        # 异步生成 embedding（不阻塞主流程）
        embedding = self._embed(content)
        if embedding:
            self._store_embedding(msg_id, embedding)
        return msg_id

    def semantic_search(self, query: str, top_k: int = 5) -> list[dict]:
        """语义检索：向量相似度 + FTS5 混合"""
        q_vec = self._embed(query)
        # 1. 向量搜索
        vec_results = self._vector_search(q_vec, top_k * 2)
        # 2. FTS5 关键词搜索
        fts_results = self.search(query, top_k * 2)
        # 3. 融合去重排序
        return self._merge_results(vec_results, fts_results, top_k)

    def get_recent_context(self, session_id, n=8) -> str:
        """获取最近 N 轮对话原文"""
        recent = self.recent(session_id, limit=n)
        return "\n".join(f"{'用户' if r['role']=='user' else 'Firefly'}: {r['content']}"
                        for r in recent)

Step 2：新增自动摘要模块

class SessionSummarizer:
    """会话摘要器：每 N 轮自动压缩对话历史"""

    def __init__(self, llm, interval: int = 10):
        self.llm = llm
        self.interval = interval
        self.turn_count = 0
        self.summary = ""

    def maybe_summarize(self, messages: list[dict]) -> str:
        self.turn_count += 1
        if self.turn_count % self.interval == 0:
            self.summary = self._do_summarize(messages)
        return self.summary

    def _do_summarize(self, messages: list[dict]) -> str:
        prompt = "请将以下对话压缩为一段简洁摘要，保留关键决策和信息：\n\n"
        prompt += "\n".join(f"{m['role']}: {m['content']}" for m in messages[-20:])
        return self.llm.chat([{"role": "user", "content": prompt}])

Step 3：修改 Firefly.respond() — 集成三层记忆

def respond(self, user_text: str) -> str:
    self._set_state("thinking")
    try:
        self.memory.add(self.session_id, "user", user_text)

        # === 三层记忆组装 ===

        # Layer 1: 缓冲层（最近 8 轮原文）
        buffer_ctx = self.memory.get_recent_context(self.session_id, n=8)

        # Layer 2: 摘要层
        summary_ctx = self.summarizer.maybe_summarize(
            self.memory.recent(self.session_id, limit=20)
        )

        # Layer 3: 语义层（跨会话长期记忆）
        semantic_hits = self.memory.semantic_search(user_text, top_k=5)
        semantic_ctx = self._format_recall(semantic_hits)

        # 组装 System Prompt
        self.llm.system_prompt = self._build_prompt(
            buffer_ctx, summary_ctx, semantic_ctx
        )

        # ... 正常对话流程 ...
        reply = self.llm.chat(messages)
        return reply
    finally:
        self._set_state("idle")

Step 4：Embedding 模型集成

class LocalEmbedder:
    """本地 Embedding 模型（ONNX 推理）"""

    def __init__(self, model_path: str = "models/m3e-base"):
        try:
            from sentence_transformers import SentenceTransformer
            self.model = SentenceTransformer(model_path)
            self._available = True
        except ImportError:
            self._available = False
            print("⚠️ sentence-transformers 未安装，语义检索降级为关键词模式")

    def embed(self, text: str) -> list[float] | None:
        if not self._available:
            return None
        return self.model.encode(text).tolist()

    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        if not self._available:
            return []
        return self.model.encode(texts).tolist()

关键设计决策

决策点选择理由
Embedding 模型m3e-base（本地）中文效果好，ONNX 可打包，无网络依赖
向量存储SQLite BLOB + 纯 Python 相似度零额外依赖，小规模（<10万条）性能足够
混合策略向量 70% + FTS5 30% 加权语义为主，关键词兜底
摘要触发每 10 轮自动触发平衡压缩率和信息损失
降级策略向量不可用时纯 FTS5保证任何环境都能工作
  • 三层互补：连贯性 + 压缩 + 语义搜索全覆盖
  • 优雅降级：向量不可用时自动退化为关键词模式
  • 本地运行：数据完全隐私，无外部依赖
  • 渐进实现：可先做 Layer 1+2，再加 Layer 3
  • 参考了 OpenClaw、Mem0 等成熟项目的架构
  • 打包体积增加 200-400MB（Embedding 模型）
  • 实现周期 5-7 天
  • 摘要质量依赖 LLM 能力
  • 需要处理 embedding 缓存避免重复计算
适用场景（强烈推荐）

这是流萤项目的最佳方案。它在复杂度和效果之间取得了完美平衡，且与现有 SQLite 架构天然兼容。建议分两期实施：一期做 Layer 1+2（摘要 + 缓冲），二期加 Layer 3（向量检索）。
